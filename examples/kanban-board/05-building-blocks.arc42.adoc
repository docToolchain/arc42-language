= Building Blocks

== Frontend

The Frontend is a single-page application built with React 19 and TypeScript. It provides
the visual Kanban board interface: board/column/card management, drag-and-drop interactions,
and real-time updates. All backend communication is routed through the API Gateway — the
Frontend never contacts downstream services directly. Team members and administrators access
the system exclusively through the Frontend web application.

== API Gateway

The API Gateway is the single external entry point for all client traffic. It validates JWT
tokens on every inbound request, applies rate limiting per tenant, and routes requests to the
appropriate downstream service. It handles the OAuth2 callback from the Identity Provider
and delegates token issuance to the Auth Service.

[source,arc42]
----

requires: if-auth-api, if-board-commands, if-board-queries, if-cache
:::
----

== Auth Service

The Auth Service handles user authentication, token issuance, and token validation. It
integrates with the external Identity Provider via OAuth2/OIDC and issues signed JWT tokens
on successful authentication. It does not store session state — all state is encoded in
the JWT.

== Board Service

The Board Service owns all board, column, and card domain state. It persists every mutation
as an event in the PostgreSQL event store (event sourcing), publishes card-updated events to
RabbitMQ via the Board Events interface, and exposes REST APIs for the API Gateway. It
maintains a Redis-cached read-model for fast board queries.

[source,arc42]
----
:::ignore H014 demo-only workspace — no implementation paths available :::
:::building-block
id: bb-board-service
title: Board Service
technology: Node.js / Express / TypeScript / PostgreSQL
implements: concept-event-sourcing, concept-logging, concept-multi-tenancy, concept-caching, concept-health-endpoints
requires: if-board-db, if-cache, if-board-events
:::
----

== RabbitMQ

RabbitMQ is the message broker that decouples the Board Service from the Notification
Service. The Board Service publishes card events to a topic exchange; the Notification
Service subscribes to those events for delivery. RabbitMQ owns the exchange contract.

[source,arc42]
----
:::ignore H014 demo-only workspace — no implementation paths available :::
:::building-block
id: bb-rabbitmq
title: RabbitMQ
technology: RabbitMQ 3.13
implements: concept-async-notifications
:::
----

=== Board Events Interface

The Board Service publishes card-created, card-updated, and card-moved events to this
RabbitMQ topic exchange. The Notification Service subscribes to these events to trigger
outbound notifications to affected team members.

== Notification Service

The Notification Service is a stateless consumer that listens for domain events on RabbitMQ
and delivers notifications to users via Slack webhook. Failures in notification delivery do
not block or affect board operations.

=== Slack Webhook Interface

The Notification Service posts JSON payloads to Slack's incoming webhook URL. This is an

It is modelled here because the Notification Service owns the integration contract.

== PostgreSQL

that forms the audit trail and source of truth for all board state. Schemas are managed by
versioned migrations.

== Redis

Redis is the distributed cache used by the Board Service to store board read-models and by
the API Gateway for per-tenant rate-limiting counters. Cache keys always include the
`tenantId` to prevent cross-tenant data access.
