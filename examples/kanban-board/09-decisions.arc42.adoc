= Architecture Decisions

== Microservice Decomposition over Monolith

The team evaluated a modular monolith and a microservice architecture. The monolith would
have been simpler to operate initially but would not have supported independent deployments
or the on-premise packaging requirement (where customers may deploy only a subset of
services). Microservices were chosen to satisfy the maintainability and reliability goals.

== Event Sourcing for Board State

The team considered standard CRUD persistence (update-in-place) and event sourcing for the
Board Service. CRUD is simpler but loses the mutation history that audit requirements demand.
Event sourcing was chosen because it provides a built-in audit trail, supports point-in-time
replay, and aligns with the GDPR right-of-access requirement without a separate audit log.

== JWT Stateless Authentication

The team evaluated server-side session storage and stateless JWT tokens. Server-side
sessions require a shared session store that becomes a single point of failure and complicates
horizontal scaling. Stateless JWTs were chosen to allow the API Gateway to scale horizontally
without coordinating session state, satisfying both the performance and security goals.

== Redis for Read-model Caching

The team evaluated serving board read-models directly from PostgreSQL event replay on every
request. Under concurrent load this would saturate the database. Redis was chosen as an
explicit caching layer to offload read traffic and provide sub-300ms board load times under
the performance quality scenario.

== RabbitMQ for Asynchronous Notification Delivery

Direct HTTP calls from the Board Service to the Notification Service would couple their
availability. If Slack is unavailable the Board Service would block or fail. RabbitMQ was
chosen to decouple these services: the Board Service publishes events without waiting for
delivery, and the Notification Service retries independently.

== TypeScript Across Frontend and Backend

The team evaluated using Go or Java for the backend services. TypeScript was chosen for all
services to enable shared type definitions between the API Gateway contract and the Frontend,
reduce context-switching for full-stack developers, and enforce a single lint and formatting
rule set. This is also a team convention constraint.

== REST and RabbitMQ as Internal Communication Standards

The team standardised on HTTP/REST for synchronous service-to-service calls and RabbitMQ
for asynchronous event flows. gRPC and other binary protocols require additional tooling
and steeper onboarding for a TypeScript-first team. The REST + AMQP combination provides
sufficient performance while keeping the communication model simple and observable.

== CI Performance Gate with k6

The absence of an automated performance regression gate means regressions reach production
undetected. A nightly k6 load test suite with p95 threshold assertions will close this gap
and make the performance quality goal continuously verifiable.

services. OpenTelemetry tracing with a Jaeger or Tempo backend will be integrated in the
sprint after initial release, providing span-level visibility across all service boundaries.
