## Goal
Support explicit, source-controlled suppression of individual arc42 validation rules in an
` ```arc42 ` fenced document, using the issue's `:::ignore RULE [reason] :::` directive.
Suppressed diagnostics must not affect validation status or normal diagnostic output.
## Key Decisions
- Ignore directives are document-scoped and match rule codes case-insensitively.
- The parser will retain the directive and optional reason as first-class document metadata;
  directives outside an `arc42` fence remain ordinary Markdown and do not suppress rules.
- Suppression is applied after all rules run, so rules remain unchanged and the behavior is
  available through both the core API and CLI.
- Filtering belongs inside `validate()` after rule execution; `validateWorkspace()` therefore
  continues to consume the already-filtered result and recompute validity through its existing
  path.
- The issue's inline form is supported literally: `:::ignore RULE [reason] :::`. Ignore nodes
  are extracted into `Workspace.ignoreDirectives`; they are not model elements or parse errors.
- A diagnostic is suppressed only when its file matches the directive's file. Workspace-level
  rules therefore follow the existing reported-file location convention.
- The first-use attention workflow and `arc42 get ignores` are deferred: this change exposes
  directive metadata for a later query without introducing persistence or a new command.
- Ignore nodes are non-semantic for architecture diff analysis and are excluded from block-change
  consistency checks.
- A bare or otherwise malformed `:::ignore` line is consumed as an inert ignore node (not an
  unknown architecture block and not E005); it has no suppression effect. This prevents the
  existing generic block parser from turning a typo into an unrelated parse error.
- Each directive is tracked as used when it suppresses at least one matching diagnostic in the
  same file. An unused directive produces a visible warning at the directive's line, making stale
  ignores self-cleaning as rules or documents evolve.
- Stale-ignore diagnostics are generated by the suppression pass rather than a normal rule and
  cannot be suppressed by another ignore directive. Unknown rule codes are also unused and thus
  produce the stale-ignore warning.
- Stale-ignore diagnostics use code `W019`, severity `warning`, and the directive's source file
  and line. `W019` is intentionally produced by the suppression pass rather than registered as a
  normal architecture rule because it depends on per-run directive usage state.
- Implementation will follow TDD: every behavior is first expressed as a focused failing test,
  then implemented minimally, then refactored while the full suite remains green.

## Notes
- No requirements, architecture, or design documents exist under `.vibe/docs`; the issue and
  existing code conventions are the source of truth for this change.
- Existing `DocumentAst` nodes already preserve source locations, while `Workspace` is the
  hand-off point consumed by validation. This makes suppression metadata additive and avoids
  changing any individual rule.
- Side effects and mitigations: adding a new AST union member may require exhaustive consumers
  (notably diffing or web rendering) to handle it; those paths will explicitly skip it. Adding
  `Workspace.ignoreDirectives` is backward-compatible for TypeScript consumers but changes raw
  serialized workspace payloads by one additive field. Suppressing an error intentionally can
  make `valid` become true, so the feature must be documented as capable of hiding structural
  failures. No CLI-specific change is needed because the CLI already renders the core result.
- The only deliberate semantic change is post-validation filtering: rule execution remains
  unchanged, but matching diagnostics disappear from output and no longer determine exit status.
  There is no persistence, cache, or cross-file suppression state, so repeated validation runs
  remain deterministic.
- This adds one intentional new diagnostic category (the stale-ignore warning). It is emitted
  after filtering, so it cannot accidentally be hidden by the stale directive itself and keeps
  ignored diagnostics from reappearing as false positives.

### Implementation strategy
1. Extend the AST with a source-located `IgnoreNode` and include it in `DocumentAst.nodes`.
2. In the line-oriented parser, recognize the inline directive before normal `:::` block
   handling, but only while the current fence is an `arc42` fence. Preserve rule, reason, file,
   and line; do not expose the directive as an architecture block. Intercept bare/malformed
   `:::ignore` forms as inert nodes so they cannot become generic unknown blocks.
3. Add an additive `IgnoreDirective` model and workspace collection. Have the builder collect
   ignore nodes while building each document, without passing them through `KNOWN_BLOCK_TYPES`.
4. In `validate()`, run the existing built-in rules unchanged, match diagnostics to directives
   by file and normalized code, mark matching directives used, and remove the matched diagnostics.
   Then append one stale-ignore warning per unused directive, using the directive location. The
   warning is not passed through suppression matching. Recompute `valid` from the resulting
   diagnostics, preserving ordering for existing diagnostics and deterministic ordering for new
   warnings.
5. Make diff consistency traversal ignore the new node kind so adding suppression metadata does
   not look like an architecture change.
6. Test positive suppression, case-insensitive codes, reasons and line locations, multiple
   directives, outside-fence non-suppression, malformed directives, unknown codes, stale ignores,
   duplicate ignores, and unchanged behavior with no directives.

### CLI strict
7. Add `--strict` flag to `validate` and `diff` commands; evaluate at command boundary.
   Normal exit behavior is unchanged; `--strict` returns 1 when any hint is present.

### Key Decisions
- `Workspace.ignoreDirectives` is optional for source compatibility with callers constructing
  workspaces manually; builder-created workspaces always provide the collection.
- Matching is case-insensitive by diagnostic code and exact by source file. Every matching
  directive is marked used, so duplicate directives are not incorrectly reported stale.
- Existing warning diagnostics remain visible after suppressing an error; validity is determined
  only by remaining error diagnostics in `validateWorkspace`.
- Bare ignore markers outside an `arc42` fence are inert prose and cannot create E005 parse errors.
- Parser directive matching is centralized before generic block opening; malformed multiline
  directives retain an inert node instead of being silently dropped.
- Validation resets directive usage before each run, making repeated validation of the same
  workspace deterministic while preserving the additive `used` metadata.
- CLI strictness is evaluated at the command boundary: normal exit behavior is unchanged, while
  `validate --strict` and `diff --strict` return 1 when any hint is present.
